## 1. コード読解メモ（リスト通読）

- ap26.Color: BLACK=+1, WHITE=-1, NONE=0, BLOCK=3。getValue() を評価で利用。
- ap26.Board: 6x6=36マス。score()=黒石-白石。
- MyEval.value(): 終局なら 1_000_000*score（勝ち筋を最優先）、非終局はマス重みMの線形和。
- MyPlayer: α-β法。**白番のときは flipped() で盤を反転し常に黒視点で探索**。
  最善手は戻り値でなく副作用 this.move（depth==0でのみ更新）で持ち回る。
  order() は Collections.shuffle で同点手をランダム化。
- isTerminal: `board.isEnd() || depth > depthLimit`。
  → depthLimit=2 だと depth 0,1,2 で着手し depth3 で評価 = **実際は3プライ先読み**(depthLimit+1)。
- MyBoard.placed(): 反転できない不正手は元盤面を返す（防御的）。BLOCK は反転線で壁扱い。

## 2. 実験3（コード読解で生じた疑問3つと自分たちの答え）

Q1. なぜ白番で盤を flipped() して「常に黒視点」で探索するのか？
  A. 対称性の利用。評価 MyEval が黒視点で書かれているため、盤を反転すれば
     「反転後の黒(=元の白)」の優劣を同じコードで評価できる。
     結果として maxSearch=常に黒手、minSearch=常に白手と固定でき、
     探索本体から色の分岐を完全に排除できる（コードが半分になる）。

Q2. なぜ最善手を戻り値でなく副作用 this.move で持ち回るのか？
  A. unit0 の抽象 α-β（戻り値=評価値floatのみ）とメソッドシグネチャを揃えるための簡略化。
     ルート(depth==0)で α が更新された手だけ this.move に保存する。
     本来は (評価値, 最善手) を構造体で返すのが綺麗だが、教材では学習しやすさを優先。
     全枝が初期αと同点だと α更新が起きず move=null になるため、
     ループ前に moves.get(0) を仮登録するフォールバックがある。

Q3. depthLimit の境界が `depth > depthLimit`（>= でない）なのはなぜ／何手読むのか？
  A. depth0 から着手を始めるので、depthLimit=2 のとき展開されるのは
     depth0(黒)・depth1(白)・depth2(黒) の3層の着手、評価されるのは depth3 の局面。
     つまり**先読み手数 = depthLimit + 1 プライ**。「深さ0でも1手は読む」設計。

## 4. 測定結果（生データ）

### 実験1: depthLimit と勝率（vs RandomPlayer 各50局, 先後25局ずつ）
```
depthLimit=0 : 39勝  7敗 4分  勝率 78.0%
depthLimit=1 : 44勝  4敗 2分  勝率 88.0%
depthLimit=2 : 45勝  3敗 2分  勝率 90.0%
depthLimit=3 : 49勝  1敗 0分  勝率 98.0%
depthLimit=4 : 50勝  0敗 0分  勝率 100.0%
```
考察: 読みを深くするほど単調に勝率が上がる。depth0(評価1段)でも78%あり、
マス重み評価自体が乱択より十分強い。depth3以降はほぼ取りこぼしなし。

### 実験2: order() の shuffle 有無（depth=2, vs Random 各50局）
```
shuffle 有 : 45勝 3敗 2分  勝率 90.0%
shuffle 無 : 48勝 2敗 0分  勝率 96.0%
```
考察: 対 Random では shuffle無の方がわずかに高い。これは「同点時に毎回同じ手を選ぶ
決定論的挙動」が、たまたま乱択相手に有効な一本道に固定されたため（=相手が学習しない
Randomなので単調化のデメリットが出ない）。本来 shuffle は「人間/AI相手に手を読まれて
固定パターンを突かれるのを防ぐ」のが目的であり、Random相手の50局では真価が出ない。
差は数局で統計的に小さく、ノイズの範囲とも言える。

### 課題1c: MyPlayer(depth=2) vs RandomPlayer 200局（先後各100）
```
177勝 18敗 5分  勝率 88.5%（得点率89.8%）
```

### 課題1d: 重み行列Mの改良（depth=2, 各100局）
```
(1)改良前 vs Random : 92勝  8敗 0分  勝率 92.0%  ← ベースライン
(3)改良後 vs Random : 94勝  5敗 1分  勝率 94.0%
(4)改良後 vs 改良前 : 89勝  6敗 5分  勝率 89.0%
```
判定: (3)-(1)= +2pt、(4)=89%(>50%)。改良前に対する直接対決で圧勝のため**改良は有効**。
理由: 角(45)とXマス/Cマス(負)を明確に区別したことで、角の取り合いで優位に立てる。

### 課題1e: phi評価（マス重み+機動力+石数, depth=2, 各100局）
```
phi vs Random        : 99勝  1敗 0分  勝率 99.0%
phi vs 改良マス重み   : 30勝 61敗 9分  勝率 30.0%   ← 負け越し!
```
考察(重要・正直な失敗): phiは Random には 99% と非常に強いが、
より強い「改良マス重み(1d)」相手には 30% と**負け越した**。
→ 「Randomに勝てる」は弱い基準にすぎない。機動力・石数項の手調整重みが
中盤の評価を歪め、depth2の浅い読みでは位置評価単体の方が安定していた。
改善案: 重みを対局データで自動調整(ロジスティック回帰/自己対戦)、
終盤の石数項のみ残し序中盤は位置評価中心にする、段階判定の閾値を再調整する。

### 課題1f: move ordering の枝刈り効果（depth=4, 各40局, value()呼出回数）
```
ランダム順    : 評価呼出   650,207 回  勝率 97.5%
move ordering : 評価呼出 2,238,040 回  勝率 100.0%
削減率: -244.2%（=増加）
```
考察(正直な失敗): 勝率は上がったが、評価呼出は約3.4倍に**増えた**。
原因: 全ノードで全子手を1手進めて評価し整列するため、整列コスト(浅い評価)が
α-βカットの削減量を上回った。6x6・depth4は元々探索木が小さく、
「整列の精度 vs 計算時間」のトレードオフで時間側に倒れた典型例。
（注: CountingEvalは整列用の浅い評価も全て計上する全仕事量メトリクス）
改善案: 整列キーをもっと安価に(置換表のスコア/マス重みのみ)、
ルート近傍の数層だけ整列、killer-move/履歴ヒューリスティックで全評価を避ける。
