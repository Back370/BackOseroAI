課題 2a (基礎 / ex2a)
総当たり戦を管理するためのパッケージ ap26.league の使用方法を理解せよ。本演習で使用するソース
ファイルは Moodle から取得すること。
第 1 回演習指示書で扱った myplayer/MyPlayer 等は、単独でゲームを進めるドライバ (MyGame) しか持

課題 2b (応用 / ex2b)
プログラミング応用杯のための最強のプログラムを実装せよ。
開発のアドバイス
1. 動くものから始めて段階的に強くする: 最初から完璧を目指さず、「合法手を返すだけ」→「貪欲法」
→「深さ 2 の α-β」→「深さ可変、評価関数強化」のように段階的に強くすること。各段階でリーグ
戦が完走することを確認してから次へ進むと、最後にどこで壊れたかが分かりやすい。最終提出直前
の大改造はリスクが高い。
2. バージョン管理 (git) の使用を推奨: チーム開発では git の使用を推奨する。GitHub や GitLab の
private リポジトリでブランチ運用すれば、複数人が並行作業しやすい。最低限、毎日コミットして
「動いた状態」を残すこと。最終提出直前の致命的バグで容易にロールバックできるようにしておく。
3. チーム内コミュニケーションを密に取る: チームの強みは役割分担にある。例えば「探索アルゴリズ
ム担当」「評価関数担当」「テスト・運用担当」のような分担と、定期的な進捗共有・コードレビュー
を推奨する。互いの作業を理解せずに統合すると統合段階で衝突する。
4. テストをしっかり行う: 新機能を追加するたびに、ベースライン（p26x00.OurPlayer、
ap26.league.RandomPlayer）との対戦で勝率を比較すること。統計的に有意な差を見るには各構成
で 100 局以上が目安。ただし、開発時間を考慮すること（局数を増やしても改善判断ができない局面
では、対局時間を縮めて手数を稼ぐ、まず少数局で方向性を見てから本数を増やす、など工夫するこ
と）。変形盤面（BLOCK あり）と標準盤面の両方で確認すること。

5. 棋譜から学ぶ: リーグ実行ログには各ゲームの棋譜（d2e4c5b3... のような文字列）が出力される。
これを盤面に書き起こして、自分の AI がどこで負けたかを分析すると改善点が見える。同じパター
ンで負けが続く場合、評価関数や手順並び替えに問題がある可能性が高い。
6. ボトルネックの発見にはプロファイラを使う: 「ここが遅いだろう」という直感は外れることが多い。
Java Flight Recorder (JFR)、async-profiler、VisualVM 等を使って思考時間の内訳を計測してから最
適化対象を決めること。早すぎる最適化は害になる（Premature optimization is the root of all evil.
– D. Knuth）。
7. 提出期限にバッファを残す: 期限ぎりぎりまで開発しないこと。期限の 2∼3 日前には完成版を提出
する想定で、最後の数日はバグ修正と最終チェックに充てる。cse 環境への移行時にローカル動作と
の差異が出ることもあるので、本番環境でのリハーサルを早めに行うこと。

課題 2c (応用 / ex2c)
発表資料を作成し、発表練習をせよ。発表には以下の 3 点を必ず含めること。
1. 探索速度（ノード/秒）を報告すること。計測は本番環境（cse.cs.nitech.ac.jp）で行うこと（ロー
カル PC の値はマシン性能に依存して比較不能なため）。標準盤の初手から終局まで 1 局実行し、そ
の間に探索した総ノード数を総思考時間で割った値を示せ。あわせて高速化のポイント（何を実装し、
どの程度の高速化に寄与したか）を説明すること。
2. 評価関数を報告すること。採用した評価関数の方針と構成を示し、ベースラインに対する勝率の改善
幅を報告せよ。性能向上のポイントを説明すること。
3. 上記以外の工夫を説明すること。例: 反復深化、終盤完全読み、並列化、リソースファイル（学習済
みモデル）の活用、独自のドメイン知識による補正、変形盤面への対応 等。チームの独自性を打ち出
す部分である。
